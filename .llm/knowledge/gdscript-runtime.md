# GDScript Runtime Facts

Verified facts about how the GDScript runtime reports a failure. Evidence cites
a command, a file:line or a measurement; re-verify on touch.

| Fact | Evidence | Verified |
| --- | --- | --- |
| A GDScript runtime error aborts the innermost function and the caller resumes, so a test case that dies inside a nested helper still reaches `context.finish()` and the engine alone reports that case as passed with a truncated assertion count. | `tests/runner-controls/control_suite.gd:29-31` with `godot --headless --path . --script res://tests/runner/run_tests.gd -- --suite res://tests/runner-controls/control_suite.gd --filter nested_abort` prints `FORTRESS_TEST_RESULT {"passed":true,…}` on Godot 4.3 | 2026-10-22 |
| A logger can be compiled at runtime with `GDScript.new()` plus `source_code` and `reload()`, so a repository never needs a script that an older pinned engine cannot parse. | `tests/runner/run_tests.gd` compiles its logger source only after `ClassDB.class_exists("Logger")`, and the same file parses on Godot 4.3 | 2026-10-22 |
| A custom logger only receives script errors when it filters on `error_type`: `push_error` reports `ERROR_TYPE_ERROR` and `push_warning` reports `ERROR_TYPE_WARNING`, while a runtime error reports `ERROR_TYPE_SCRIPT`. | The logger recorded `error_type: 2` for a runtime error, `0` for `push_error` and `1` for `push_warning` on Godot 4.7.2 | 2026-10-22 |
| GDScript has no `try`/`catch`, so a case cannot catch its own runtime error. | `try:` is a parse error ("Expected end of statement after expression, found \":\" instead.") on Godot 4.3 and 4.7.2 | 2026-10-22 |
| Moving the completion marker into the case body does not detect an abort: the body resumes after the aborted helper and still reaches the marker. | A suite whose marker sits at the end of the case body printed `FORTRESS_TEST_RESULT {"passed":true,…}` with `assertions: 1` for a case that died inside a nested helper, on Godot 4.3 and 4.7.2 | 2026-10-22 |
| A Godot 4.7.2 engine hands a script error to a custom logger: `OS.add_logger` with a `Logger` subclass that overrides `_log_error` receives the message, the file and the line. | The logger printed `LOGGER ERROR: res://probe.gd:13 Out of bounds get index '4' (on base: 'Array[int]')` for the same runtime error | 2026-10-22 |
| The runner reports an aborted case on both pins: it uses the custom logger on Godot 4.7.2, and on Godot 4.3 it supervises a child process that writes its merged output to an engine log file. The registered logger is removed before the process exits, because the engine otherwise reports its script resource as still in use. | The same control prints `FORTRESS_TEST_RESULT {"passed":false,…,"kind":"case_aborted"…}` and `FORTRESS_TEST_ABORT_WATCH {"available":true,"errors":2}` on 4.7.2 and 4.3 | 2026-10-22 |
| Godot 4.3 has neither the `Logger` class nor `OS.add_logger`, so that engine cannot observe a script error in process, and it has no `OS.get_temp_dir`. | `Could not find base class "Logger".` on 4.3, `OS.has_method("add_logger")` is false there, and `OS.has_method("get_temp_dir")` is false there against true on 4.7.2 | 2026-10-22 |
| Godot writes the merged engine output to `--log-file` while the process runs, and that file prefixes error lines with `USER ` (`USER SCRIPT ERROR:` against `SCRIPT ERROR:` on stdout). | A watchdog control's `--log-file` contained `FORTRESS_WATCHDOG_ENTERED` within three seconds, and the nested-abort control's log contained `USER SCRIPT ERROR:` with the expected `at:` line | 2026-10-22 |
| The engine writes the script error to stderr and the runner's progress records to stdout, so the order that names the case that was executing only survives in one merged stream. | `scripts/run_godot_tests.py:229-230` merges the two streams; the attribution walks the merged order in `engine_errors` | 2026-10-22 |
| Hex or decimal integer literals above the signed-64-bit maximum fail to parse and poison the whole script's constant pool, so unrelated code fails afterwards; 64-bit hashing needs computed constants (`0xcbf29ce4 * 4294967296 + 0x84222325`), may rely on documented int64 wrap for the multiply, and must format through 32-bit halves (`"%08x%08x" % [(v >> 32) & 0xFFFFFFFF, v & 0xFFFFFFFF]`) because `"%016x"` renders a negative top-half as signed. | A trace script using `0xcbf29ce484222325` printed `ERROR: Cannot represent 0xcbf29ce484222325 as a 64-bit signed integer` from `hex_to_int` and then failed an unrelated artifact-schema check; the wrap probe printed `basis=-3750763034362895579` and `hex=af63bc4c8601b62c`, matching Python's unsigned `masked` exactly | 2026-11-14 |
| `JSON.parse` hands whole numbers to typed checks as floats on the pins, and `int()` truncates silently, so an artifact-mutation gate must verify whole-number-ness (`value == floor(value)`) before an `int()` comparison or a `players: 3.5` mutant passes as 3. | `tests/oracle/sync_floor_trace.gd` accepted a float player-count mutant until `_whole` guards were added; after them the same artifact exits 2 with `sync floor oracle: artifact outside the canonical floor configuration` on Godot 4.3 | 2026-11-14 |
