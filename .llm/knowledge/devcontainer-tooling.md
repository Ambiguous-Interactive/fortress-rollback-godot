# Devcontainer & Container Tooling Facts

Operational facts learned while building this repo's devcontainer
(`.devcontainer/`); feeding retrospective
[foundations archive](../retrospectives/2026-10-18-foundations-archive.md).

| Fact (one assertable sentence) | Evidence (command + output, file:line, or measurement) | Verified |
| --- | --- | --- |
| The `mcr.microsoft.com/devcontainers/base:ubuntu-24.04` image ships no python3, and devcontainer features install only `python3-minimal` (no stdlib: `json`, `unittest`, `dataclasses`), so repos needing stdlib Python must apt-install the full `python3` package in their Dockerfile before features run. | `/var/log/apt/history.log` in container: `apt-get -y install --no-install-recommends python3-minimal`; `python3 -c "import dataclasses"` → `ModuleNotFoundError` before fix, pass after. | 2026-10-09 |
| Devcontainer features execute in layers AFTER the Dockerfile build, so a feature-installed runtime (e.g. Node via the node feature) is invisible to Dockerfile `RUN` layers; runtimes needed at build time must be installed in the Dockerfile itself. | Build failure: `npm: not found` semantics — godot-mcp layer needed npm; fixed by installing Node in Dockerfile before features (`.devcontainer/Dockerfile`). | 2026-10-09 |
| `postCreateCommand` runs only on container CREATE; `devcontainer up` reuses an existing container after image/config changes unless `--remove-existing-container` is passed, so post-create changes can silently not run. | `devcontainer-build4.log` (failed run) and `devcontainer-build5.log` (success) report the identical `containerId`. | 2026-10-09 |
| Docker creates missing named-volume mount-point parent directories as root, making the mounted volume unwritable for the remote user; pre-create the mount points in the image and `chown` them so first-mount copy preserves ownership. | post-create failure: `/home/vscode/.cache/uv/CACHEDIR.TAG: Permission denied (os error 13)`; fixed by `mkdir -p` + `chown -R vscode:vscode` in image. | 2026-10-09 |
| `npx -y <pkg>` does NOT resolve a globally installed package — it fetches from the npm registry even when the package is already on PATH via `npm i -g`. | Reviewer empirical test with registry pointed at a dead endpoint: `npx -y @coding-solo/godot-mcp` → `FetchError ... ECONNREFUSED` despite global install. | 2026-10-09 |
| Claude Code reads credential-like environment variable names as EMPTY (with no warning) when expanding `${VAR}` in remote MCP servers' `url`/`headers`, so headers must use a custom non-credential name; stdio `env` blocks are unaffected. | code.claude.com/docs/en/mcp § "Credential variables that read as empty" ("If you write `Bearer ${ANTHROPIC_AUTH_TOKEN}`, the server receives `Bearer`... A name outside this set, such as `API_KEY`, expands as written"). | 2026-10-09 |
| GitHub `releases/latest/download/<asset>` is a download redirect that avoids the REST API quota; install scripts that query `api.github.com/repos/.../releases/latest` unauthenticated fail under the 60 req/h IP limit during container builds. | opencode installer failure `Failed to fetch version information` in build; direct asset download succeeds. | 2026-10-09 |
| Docker `--env-file` keeps quotes verbatim and treats trailing text as part of the value; `GITHUB_TOKEN="x"` and `KEY=x # comment` both corrupt the value silently. | Docker CLI documented env-file semantics; corruption modes added to `.devcontainer/devcontainer.env.example`. | 2026-10-09 |
| BuildKit rejects ARG expansion in `COPY --from` ("variable expansion is not supported for --from"); the workaround is a dedicated `FROM ... AS x` stage, and predefined args (e.g. `TARGETARCH`) must still be re-declared inside a stage to be visible in `RUN`. | Build error in first `up`; fixed via `FROM ghcr.io/astral-sh/uv:${UV_VERSION} AS uv-bin` stage. | 2026-10-09 |
| For fail-closed firewall setup, DROP policies must be the immediate successors of the filter-table flush: every fallible statement (chain deletes, NAT replay, network fetches) belongs either before the flush (gather phase) or guarded behind the policies. | Adversarial review rounds 2-4 each found a residual flush→policy window (mangle flush, xargs NAT replay, `iptables -X`); final ordering verified in `.devcontainer/init-firewall.sh`. | 2026-10-09 |
| OpenCode 2.0.26 initializes its runtime MCP catalog asynchronously, so a successful `debug config` followed immediately by `mcp list` can still report no servers in a fresh daemon. | PR #54 first fresh image runs: all three discovery checks failed on both architectures; isolated fresh-service reproduction: first list empty, second list names pending; `.devcontainer/verify-tools.sh` now polls within a fixed deadline. | 2026-10-10 |
| Devcontainers CLI 0.89.0 uses `--build-no-cache`, not `--no-cache`, to rebuild image layers without cache. | `npx @devcontainers/cli@0.89.0 up --help`; corrected `.devcontainer/README.md` command and maintenance table. | 2026-10-10 |

## npm global packages

| Fact | Evidence | Verified |
| --- | --- | --- |
| On Unix the npm global write path needs write permission on the **parent** directory, so a `root:root 0755` `<prefix>/lib/node_modules` and `<prefix>/bin` make every global write fail for the non-root `remoteUser`: `mkdir` for a new package, `rename` for an update or a removal. Read-only npm commands keep working and mask it. | Reproduced as `vscode`: `npm i -g @openai/codex` → `EACCES ... rename ... -> @openai/.codex-vdnmINeK`; `npm i -g is-number` → `EACCES ... mkdir`; `npm un -g @openai/codex` → `EACCES ... rename`; meanwhile `npm ls -g --depth=0` and `npm view @openai/codex version` succeeded. | 2026-10-18 |
| `npm doctor` does **not** detect this class of breakage: it reports every permission check `Ok` and exits non-zero only for its version recommendations. It flags group/world-writable directories, never "not writable by the current user". | `npm doctor` in the broken state: all five permission checks printed `Ok`, exit 1 came from `Not ok / Use npm v12.2.0` and `Not ok / Use node v24.22.0` — version advice, not the EACCES. Do not use `npm doctor` as the oracle for this; use a real global install/uninstall round-trip (`.devcontainer/verify-tools.sh` `check_npm_global_writable`). | 2026-10-18 |
| `npm uninstall -g` does not prune empty scope directories, so a global install/uninstall round-trip leaves `<root>/@scope/` behind; residue assertions must check the package directory and the bin symlink, never the scope directory. | After `npm un -g @frg-probe/npm-global-write-probe` the only residue was an empty `fake-prefix/lib/node_modules/@frg-probe/`; the control probe failed until the assertion was narrowed, while the package and symlink were in fact removed. | 2026-10-18 |
| setgid propagates group ownership but **not** the write bit: a global package installed afterwards by root inside a setgid global root is created `2755` (right group, no group write), and `npm uninstall -g` then fails with `ENOTEMPTY` on rename, leaving both the package and a `.pkg-XXXX` temporary behind. | `sudo npm i -g which@3.0.1` produced `drwxr-sr-x 0:1000` for `which`, `which/bin`, `which/node_modules`, `which/node_modules/isexe`; subsequent `npm un -g which` → `ENOTEMPTY: directory not empty, rename '/usr/local/lib/node_modules/which' -> '.../.which-zpa7s2T4'`, exit 217, both directories still present. Re-running the permission repair restores write and the uninstall succeeds. | 2026-10-18 |
| `npm pack --silent` prints the packed filename, and it differs from the package name for scoped packages (`@scope/name` → `scope-name-<version>.tgz`); guessing the filename makes `npm install -g <path>` fail as `tarball ... seems to be corrupted`, which is an unrelated error that can be mistaken for a permissions failure. | `npm pack --silent --pack-destination . <pkg>` → `frg-probe-npm-global-write-probe-1.0.0.tgz`; hardcoding `frg-probe-1.0.0.tgz` produced `npm warn tarball ... seems to be corrupted`. Capture the printed name instead. | 2026-10-18 |
| `verify.sh`'s git-hooks wiring check compares `core.hooksPath` against the literal string `.githooks`, so an absolute path fails the check even though git honours it equally. Anything that writes an absolute hooksPath (rather than `make hooks`) turns the acceptance harness red for a non-defect. | At pristine HEAD `git config --show-origin core.hooksPath` → `/workspaces/fortress-rollback-godot/.githooks` and the check failed; `make hooks` (`git config core.hooksPath .githooks`) restored the relative value and the check passed. Considered over-strict: compare `realpath` of both sides instead. | 2026-10-18 |
| Devcontainer features are appended as layers AFTER the user Dockerfile, so a Dockerfile step that repairs filesystem state cannot cover packages a feature installs. A root-owned package created by the claude-code feature therefore undoes the Dockerfile's npm-permission repair on every rebuild, while the Dockerfile-installed CLIs stay fixed — a half-broken state that looks like a flaky bug. | `Dockerfile:24-26` states Node is installed "before features run (the claude-code feature detects and reuses it)"; the Dockerfile never installs `@anthropic-ai/claude-code`. Simulation: perms step → `root:vscode 2775`, then a root-side install → `root:vscode 2755`, then `npm install -g` of that package → `EACCES ... unlink`. Fixed by re-applying from `post-create.sh`, which runs after features. | 2026-10-18 |
| A global-npm probe that only installs a brand-new package false-passes when the global root itself is writable but a pre-existing scope directory is not: creating `@newscope/pkg` needs write on the root, while replacing `@oldscope/pkg` needs write on `@oldscope`. Assert writability over every directory under the global root, and drive the replace path, or the probe cannot see the bug it exists to catch. | Old probe reported `PASS` against a prefix whose global root was `root:vscode 2775` but whose existing package was `root:vscode 2755`, while `npm install -g` on that package failed. Adversarial review finding; the new `check_npm_global_writable` asserts the precondition and installs v1.0.0 then v1.0.1 over it. | 2026-10-18 |
